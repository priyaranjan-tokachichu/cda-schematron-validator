Core runtime

Java 21+ hosts the HTTP service and validation engine. Saxon-HE 12.9 executes stylesheets generated by SchXslt 1.10.1. The JDK XSD validator checks the pinned CDA schema, including approved SDTC extensions. Gson serializes the report. No database, message broker, application framework, or Node process is required inside the runtime container.

Startup work versus document work

  1. Verify bundled artifact inventory checksums and load the pinned source manifest.
  2. Compile the schema once. Compile each official Schematron profile once and retain immutable executables.
  3. Normalize the releases' omitted query binding using backwards-compatible XPath 1.0 expression semantics, make phase severity explicit, and assign deterministic IDs to assertions without IDs. Original tests and rule descriptions are retained.
  4. For each request, create an independent parser, schema validator, Saxon transformer, line lookup cache, and result collector.
  5. Stream SVRL into a bounded finding collector; do not build an unlimited intermediate report. Return findings and provenance, then release document references.

Trusted vocabulary XML can be cached as immutable trees under verified asset paths. No patient-document or validation-result cache is used. The HTTP layer uses virtual request threads and a fixed validation pool; default capacity is two active validations and four waiting submissions.

Security boundaries

DTD declarations and external entities are rejected. Runtime resource resolution denies network access and files outside the bundled asset root. The public API accepts XML text and installed profile IDs, never arbitrary server paths, remote documents, or uploaded Schematron. Request bodies, document filenames, finding text, and XML parser diagnostics are not written to application logs.

Update policy

A weekly GitHub workflow checks official latest releases and signals a mismatch with the locks. It does not replace rules or create a PR automatically. Updates require owner review, checksum changes, coverage review, official-package tests, and fresh benchmark evidence. Base container images and CI actions are also pinned by digest or commit.

HL7 also supports validating CDA through FHIR StructureDefinitions. That is a possible future adapter for broader coverage, not a capability claimed by the current Schematron implementation. See HL7 validation guidance and the official generator. Original code attribution remains with Eric Wadkins and subsequent work by Priyaranjan (Raj) Tokachichu; John D'Amore's sample repository is credited as a sample source.

Findings contain severity, stage, source message, rule ID, XPath, assertion test, pattern/context, and available line/column locations. Missing upstream assertion IDs receive stable generated IDs scoped to the pinned artifact. Suggestions are not fabricated; the original rule and its requirement are provided for investigation.

  • valid: no errors, configured stages completed, no truncation, a supported document-level template, and no recorded generation gaps.
  • invalid: errors found. Completeness must still be inspected.
  • incomplete: no errors found, but execution or coverage is incomplete. This is not a pass.

executionComplete describes configured engine execution; validationComplete additionally accounts for recorded generation gaps and truncation. Finding messages can contain submitted document values and must be handled as sensitive by the caller. The modern API does not return XML snippets.

HTTP 200 means a validation report was produced, not that the document passed. Invalid requests use 400/413/415/422, missing authentication uses 401, saturation uses 429, engine failures use 500, and the deadline uses 504. Engine failures may return a partial report with completeness false.

05Interface and interaction design

The workspace keeps the primary task visible: choose or paste XML, select the implementation guide, validate, and inspect findings. A restrained green/neutral palette distinguishes actions from red errors and amber coverage gaps. The layout stacks at mobile widths without page overflow.

  • UTF-8 file chooser, drag-and-drop input, paste editor, line gutter, document size, and a synthetic example.
  • Installed profile selection, pinned release metadata, warning toggle, and expandable coverage details.
  • Stage status, error/warning totals, rules fired, measured duration, finding filters, and expandable rule/XPath information.
  • Click a location to select the relevant XML line. Download the full report as JSON.
  • Input and configuration controls are locked during validation. Editing the document or settings invalidates stale results.
  • No external fonts, scripts, trackers, analytics, or rendering libraries. User-derived findings are inserted as text rather than HTML.

The multi-stage build fetches and verifies official assets separately, builds and tests the Java service, then copies only the JRE, assembled application, UI, notices, and assets into the runtime image. The container runs as UID/GID 10001, with a read-only root filesystem, temporary filesystem, dropped capabilities, no-new-privileges, and CPU/memory/PID limits. The Compose port is bound to localhost.

For shared deployments, configure API_TOKEN, an authenticated HTTPS gateway, appropriate access controls, and proxy/client logging policy. No database or persistent patient-document volume is required. Stateless replicas can be placed behind a gateway; each replica owns its compiled profiles and bounded workers.

An owner-triggered release workflow is prepared to publish AMD64 and ARM64 images to GitHub Container Registry using the workflow's scoped token, with SBOM and provenance output. It does not publish on a PR or merge. Registry artifact availability is recorded in the GitHub release; this report documents implementation verification, not a production deployment.

Operational boundaries

Default maximum XML: 20 MiB (20,971,520 bytes), configurable through MAX_XML_MIB. The API advertises active limits and the UI follows them. The HTTP JSON allowance is six times the XML limit plus 64 KiB (default 120 MiB + 64 KiB), allowing worst-case JSON escaping. Provision memory and heap for larger workloads. Serialized JSON is streamed rather than buffered; only bounded decoded fields are retained. Uploads share a budget of one quarter of the maximum heap, with conservative reservations made before reading (smaller for known-length bodies, full allowance for chunked bodies). Admitted uploads queue fairly for up to 30 seconds instead of failing on memory contention. Default total request capacity is six. Only a full request queue returns HTTP 429; an expired upload queue wait returns HTTP 503. Health checks stay available. Increase Java heap and container memory to permit more concurrent large uploads; CPU and document complexity also affect speed. Reservations are released on success, malformed or oversized input, and disconnect. Unknown or duplicate fields are rejected; profile IDs are capped at 128 UTF-8 bytes. Document coverage requires a supported document-level template from the selected pinned profile; nested rules alone cannot establish complete validation. Pending input loads and validation responses are revision-checked to prevent stale reports. Maximum element depth: 128. Maximum elements: 100,000. Maximum attributes per element: 256. Maximum findings: 2,000. Finding messages are bounded to 4,000 characters. Upload queue wait is bounded to 30 seconds; the HTTP upload/read window to 65 seconds; validation has its own 30-second deadline; cancellation is cooperative at streamed output boundaries, not process-level hard termination of an arbitrary XPath operation.

09Legacy API and migration

The original in-process exports remain: validate, validateAsync, both batch methods, parseSchematron, and both cache-clearing methods. Their result fields and synchronous/Promise contracts are retained. They run without the Java service, but remain a partial Schematron interpreter and do not include XSD validation.

Fixes isolate document context caches, clone caller options, complete empty async patterns, preserve batch ordering, generate missing IDs, bound compiled-map caches, distinguish resource paths and file versions, and reject missing input explicitly. Previously incorrect results are fixed rather than preserved as compatibility behavior. The default legacy warning setting remains false.

The modern client is an additive export: createClient(). It submits to the HTTP service and returns the complete modern report contract. Type declarations are included. The CLI uses that same client and exits 0 for valid, 1 for invalid, and 2 for incomplete or operational failure. The supported Node baseline is 22.12+, with Node 22 and 24 configured in CI.

  • main requires a PR, including for administrators. Force pushes and deletion are disabled. Owner-authored PRs do not require another reviewer, allowing the owner to merge their own work after checks.
  • The repository owner is currently the sole collaborator with write/admin access. The added owner/branch policy check rejects non-owner PR authors as merge candidates.
  • Public issues remain enabled, with a synthetic-example bug-report form.
GitHub does not provide a control that completely prevents outside PR creation on this public repository while independently preserving public issues. This implementation documents the owner-only contribution policy and gates merging; it does not misrepresent that platform limitation.

11Known limits and future improvements

  1. Coverage: resolve or explicitly accept the upstream C-CDA 5.0 conversion gaps. A future StructureDefinition adapter and terminology service/snapshot integration require separate conformance testing.
  2. Clinical corpus: expand testing to independently adjudicated positive and negative clinical examples, template versions, nullFlavor combinations, extension handling, and large documents. The existing examples are not a clinical certification corpus.
  3. Reference comparison: compare findings with a separately configured reference validator and investigate mismatches. FHIR-based and Schematron-based checks are not automatically equivalent.
  4. Hard isolation: requests have bounded admission and cooperative deadlines. Environments requiring guaranteed per-document hard termination should add process-isolated workers with kill/restart supervision.
  5. Production performance: measure long-running throughput, saturation, memory peaks, and tail latency on the intended hardware and document distribution.
  6. Release: review the PR, require CI checks, scan the final image and dependencies, publish an explicitly versioned release, and verify public registry access if distribution is intended.
